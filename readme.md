## HU-01 — Read Card Information in a Clear and Readable Format

As a duelist, I want information such as a card's effect, statistics, or price to be displayed in a clear and consistent format, so that I can quickly understand the information without dealing with raw API data.

To implement this user story, a Pipe was created to determine the lowest available price for a specific card.
In order to keep the pipe reusable for different scenarios, it was designed to accept both arrays and objects as input. The API returns prices as key-value pairs, while in other cases the data could be provided as an array. For this reason, the pipe supports both input types:

```ts
export class CheapestPricePipe implements PipeTransform {
  transform(
    value: object | Array<unknown> | null | undefined,
    currencySymbol: string = '$'
  ): string {
    if (!value) return 'N/D';

    const rawValues = Array.isArray(value) ? value : Object.values(value);

    const numericPrices = rawValues
      .map(p => (typeof p === 'string' ? parseFloat(p) : Number(p)))
      .filter((p): p is number => !isNaN(p) && p > 0);

    if (numericPrices.length === 0) return 'No market price available';

    const minPrice = Math.min(...numericPrices);
    return `${currencySymbol}${minPrice.toFixed(2)}`;
  }
}
```

Although the pipe accepts different input types, it is still a **pure function** because it always produces the same output for the same input, does not modify its arguments, and has no side effects. This makes it deterministic and allows Angular to optimize its execution by only re-evaluating it when the input reference changes.

The `unknown` type was intentionally used for array elements because the pipe does not assume a specific data structure. Instead, each value is validated and safely converted at runtime before being processed, making the implementation more generic and type-safe.

## HU-03 — Search Without Having to Press a Button

As a duelist, I want the results to update while I type the name of a card, without having to manually confirm the search, so that finding cards feels smoother and more natural.

To implement this user story, the search component was intentionally kept free of debounce logic so that it remains fully reusable.
Instead, the debounce behavior is handled inside the service by listening to changes in the signal provided by the search component.

Initially, the service contained the following implementation:

```ts
 debouncedSearch = toSignal(
    toObservable(this.search).pipe(
      debounceTime(800),
      distinctUntilChanged()
    ),
    { initialValue: '' }
  );
```

The `httpResource` automatically performs a new request whenever the debounced signal changes.

However, Angular 22 introduced the `debounced()` utility, which greatly simplifies this pattern.
Therefore, the previous implementation was replaced with:

```ts
debouncedSearch = debounced(this.search, 800);
```

This improves code readability by keeping the entire implementation signal-based, without requiring conversions between Signals and Observables.

## HU-04 — Combine Filters Without Losing Control

As a duelist, I want to filter the catalog by card type, attribute, and/or ATK/DEF range, in addition to the card name, combining multiple criteria at the same time, so that I can find exactly the type of card I need for my strategy.

Since the application already uses `httpResource`, implementing additional filters becomes straightforward.
The only required change was adding new signals to the `CardsService`, as shown below:

```ts
export class CardsService {
  page = signal(1);
  search = signal('');

  type = signal('');
  attribute = signal('');
  ...
```

Then, inside the resource configuration, each signal is conditionally included as an HTTP parameter.
`httpResource` automatically tracks every signal dependency and performs a new request whenever any of them changes.

```ts
readonly cards = httpResource<CardsResponse>(() => ({

    params: {
```

## HU-05 — Keep My Selection While Exploring

As a duelist, I want to keep one card "in focus" (a potential favorite or future deck candidate) that I can freely compare without losing it whenever I perform another search.

Although the use of `linkedSignal` was suggested for this user story, it was considered unnecessary.
A regular `signal` is sufficient because the focused card should represent the user's explicit selection rather than automatically depend on the search results. This allows the selected card to remain unchanged even when the catalog is refreshed or filtered, preserving the user's context while exploring different cards.

For this reason, the entire state is managed using a dedicated service and a signal.

```ts
@Service()
export class CardSelectionService {
    focusedCard = signal<Card | null>(null);

    selectCard(card: Card) {
        this.focusedCard.update(previousCard => previousCard?.id === card.id ? null : card);
    }

    isSelected(cardId : number){
        return this.focusedCard()?.id === cardId
    }
}
```

## HU-06 — Load Only What Is Needed (Bonus)

As a duelist, I want secondary information about a card (such as its market price) to be loaded only when I actually need it, so that the card details feel fast and lightweight.

To implement this, the accordion component—which displays its content through `ng-content`—uses `@defer` so that the projected content is rendered only when it enters the viewport.
For demonstration purposes, a loading spinner with a minimum duration of one second was added.

Using `@defer` delays the creation and rendering of the deferred content until the specified trigger (`on viewport`) is activated. This reduces the amount of work Angular performs during the initial render, improving startup performance and avoiding unnecessary rendering of content that the user may never open or scroll to.

```html
<summary>
    {{sectionName()}}
</summary>

@defer (on viewport) {
    <ng-content>
    </ng-content>
}

@placeholder {
    <p>Loading</p>
}

@loading (minimum 1000ms) {
    <app-loading-spinner></app-loading-spinner>
}
```

## HU-02 — Search Cards by Name

* Implemented a shared `searchbox` component that exposes an `output`, allowing any page to decide what to do with the search value.

```ts
export class Searchbox {
  search = output<string>();

  onSearch(event: Event) {
    const value = (event.target as HTMLInputElement).value;
    this.search.emit(value);
  }
}
```

* The template uses **event binding** to trigger the search.

The parent component updates the Signals like this:

```ts
letsSearch(value: string) {
  this.cardsService.search.set(value);
  this.cardsService.page.set(1);
}
```

Since `httpResource` is reactive, updating either `page()` or `search()` automatically triggers a new request, so searching happens without any additional logic.

export class GreatCardsDirective implements OnInit {
 
  readonly #element = inject(ElementRef);
  readonly #renderer = inject(Renderer2);

  readonly card = input.required<Card>();

   ngOnInit(): void {
    const atk = this.card().atk;
    if(atk !== undefined && atk > 1000){
        this.#renderer.addClass(
          this.#element.nativeElement,
          'highlight-card'
        );
    }
  }
}
